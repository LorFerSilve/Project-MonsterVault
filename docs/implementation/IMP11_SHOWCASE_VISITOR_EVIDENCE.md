## Permission and consent

ShowcaseService holds P0 live Player/private Ready ProfileSession identities and targeted GUID references. Default policy is **Closed**. **Party** limits explicitly targeted grants to current present eligible members of the owner's existing Party; **SameServer** permits explicitly targeted current eligible players without a Party. Party membership alone grants nothing. The friend portion of the broader eligible Party/friend audience remains inactive until its platform binding exists; no friendship is guessed. Existing session-only invitation preference, default None/explicit SameServer, also suppresses visitor offers. Disabling it revokes incoming visitor permissions, including an active view. Full platform restricted/blocked audience integration remains a broader social/release gate.

Only the authenticated owner can choose their policy, grant or revoke. Policy/grant/revoke compare a server-owned permission revision. Revisions come from one monotonic runtime serial and never restart on Player/session replacement within the server. The visitor opens using only exact `ownerUserId` and `grantId`; the server must find that exact intended visitor identity. One visitor cannot transfer a token, target a different owner or self-authorize. Either the owner revokes or the visitor closes; closing consumes the grant. Every policy change clears outgoing grants and requires fresh consent, including widening the audience. Avatar reset alone preserves a still-current Player/session permission.

Five exact Class B intents reuse the existing three remotes and gateway: `Social.ShowcaseSetPolicy {audience}`, `ShowcaseGrant {targetUserId}`, `ShowcaseRevoke {grantId}`, `ShowcaseOpen {ownerUserId,grantId}`, `ShowcaseClose {grantId}`. The first three require the owner's current permission revision; open/close accept no expected revision or authority fields. Class A `{domain="showcase"}` resync and the Ready handshake publish the same recipient-only readback.

## Session, updates and lifecycle

Every grant/open/readback rechecks current exact native Player and private Ready ProfileSession identities. Owner or visitor replacement/unavailability revokes all affected grants and the active view; reconnect inherits no visitor entitlement. Stale cleanup cannot remove a replacement identity. Existing non-Class-A bounded replay compares private ProfileSession identity; replaced-session cached success is rejected. A duplicate grant never adds a record or renews expiry; duplicate/replayed revoke cannot remove or resurrect a newer grant.

ProfileSession has one detachable readback observer notified after a serialized writer changes state/profile. SessionCoordinator forwards only the exact current session and detaches on forget; the social runtime unsubscribes on stop. Observer failure cannot change a durable write outcome. This supplies event-driven display refresh and trust-loss cleanup, without a new writer, profile schema or polling owner. The social owner reads one filtered presentation per changed owner and shares that safe cache across visitors; it stores no full profiles. Audience reads reuse exact existing social identity records without taking full per-visitor profile snapshots.

A presentation read pins its owner identity and cache version. If a revoke, disconnect, session replacement or profile change occurs during the read, the result cannot restore permission or old content. Display clear/reassignment updates active viewers through newer full snapshots. PlayerRemoving revokes promptly; shutdown clears all identities/grants/visits/caches and invalidates the existing shared timer's ticket/generation. Stale timer/profile callbacks leave zero authority.

## Bounds, wire and minimal client

DEV bounds are **60 live identity records, two outgoing grants per owner, two incoming grants per visitor, one active view per visitor and one exact creature card**. Thus at most 120 grants exist; there is no history, queue or persistent entitlement. Grants expire after **60 monotonic seconds**, with separate immutable synced display deadlines. Grant/Open use capacity one/refill one per three seconds in the existing gateway rate owner; global budget, Ready/schema checks and 128-entry/120-second replay remain unchanged. Forged owner/visitor/session/paid/field selectors, unknown/self targets, hidden-field requests, oversized and non-finite payloads fail closed.

Two bounded full domains on existing Social.StateChanged separate permission readback from card content: `showcase` carries audience/permissionRevision and at most two outgoing/incoming `{id,userId,expiresAt}` summaries; `showcaseView` carries Closed/reason or the approved ReadOnly card. Each independently satisfies the existing **4096-byte**/depth/node budget, leaving completed Party/Challenge projection semantics intact. If complete intrinsic facts cannot fit, the whole card is withheld with `hasMore=true`; no truncated trait/rarity identity is claimed. There is no arbitrary paging or full profile replication.

The existing collapsed native social diagnostic panel shows owner policy, allowed visitors/revoke, incoming permission/open, current owner identity, the exact card, ReadOnly mode, revoked/expired/unavailable state and close/return. Incoming data never opens it or takes focus. The existing single server next-deadline owner and single client diagnostic expiry owner include Showcase; no per-visitor timer, Heartbeat or polling is introduced. PQL-2/3/4/8 retain final creature/cards/Vault/camera/UI/cosmetic presentation. Existing native UI is sufficient here; no 3D asset was added.
