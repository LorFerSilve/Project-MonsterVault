## State and consent

- `PartyService` privately owns Party GUID, membership revision, leader UserId, member seats and monotonically increasing join sequence. One participant membership index includes both present seats and disconnected reservations. Four seats is the locked maximum; no automatic switch flow exists.
- Invitations have a server GUID, Party/revision, intended UserId, exact sender/recipient live identity records and a server-monotonic deadline. Receipt of an invite grants no membership. Only its current intended invitee may explicitly accept/decline. Decline, ignore and expiry have no personal-value consequence.
- Creation explicitly joins only the creator as leader. Leader-only operations are invite, removal and disband. Any member may leave; a returning player may also release their reserved seat without rejoining. Self-invite, self-removal, unknown players/members, foreign Party IDs and already-affiliated invitees fail closed.
- Membership mutation increments Party revision and cancels invitations to the previous membership/leader revision. Acceptance compares both the invite's pinned revision and the client's expected revision to current server state. Duplicate acceptance cannot add a seat twice. First server-admitted non-yielding transition wins conflicting final-seat/cross-Party operations; no paid/status/latency priority exists.
- Like existing capture admission, transitions are non-yielding critical sections. Party-local state and the participant index are checked and changed together. Trusted adapters only read native Player/ProfileSession identity, clock or GUID; there is no multi-lock framework, persistence wait, networking callback or queued yield inside a mutation.

## Identity and lifecycle

Every mutation checks `Players:GetPlayerByUserId(UserId)` and the current private ProfileSession's Ready state. Stored member/invite authority must match the exact Player and session objects. A replacement without a trusted disconnect drops prior membership/invites/preference, rather than granting grace or copying authority. A session becoming unavailable also loses membership; the GDS allowance to retain protected social membership is optional and unused here. Avatar reset/valid travel preserve the same social identity.

Unexpected/ambiguous native Unknown departure may reserve the seat for **30 server-monotonic seconds**. Reservations retain only UserId, PartyId through the membership index, original join sequence, deadline and disconnect revision; they release Player/ProfileSession references. Reserved seats count toward four, project as absent and grant no active membership authority. The returning live Ready identity receives a rejoin offer, then must submit explicit intent at the current Party revision. Other intervening mutations require refreshed consent. Returning former leaders do not seize leadership, but retain their original join order for later succession.

Leader loss selects the longest-present currently eligible remaining member. If none is available, the Party dissolves and all reservations end. Explicit Party leave, CreatorKick/platform kick and shutdown grant no grace. Native PlayerExitReason exposes Unknown and kick categories, not an authoritative voluntary/network distinction; ordinary ambiguous Unknown therefore receives only bounded grace. [Roblox enum](https://create.roblox.com/docs/reference/engine/enums/PlayerExitReason).

Grace expiry/removal/disband releases the membership index. Old Player/session cleanup cannot remove a replacement identity; old cleanup callbacks cannot resurrect state. Shutdown cancels the timer, invalidates generation/ticket and clears every Party/invite/member/live-identity map. A different/new server has no restoration source.

## Bounds, networking and projection

DEV tuneable limits: 60 Parties, 60 live identity/preference/cooldown records, four pending outgoing invitations per Party, two incoming invitations per player, 30-second invitation/rejoin lifetimes and separate three-second sender/recipient cooldowns. Party churn does not reset a live sender cooldown. Duplicate active invitations are suppressed. There is no historical invitation list, per-Party/invite/player task loop, Heartbeat or polling. `PartyRuntimeService` owns at most **one `task.delay` deadline callback**, rearming only for pending invitations/reservations. It consumes a callback ticket before expiry/projection work; stop/rearm reject old callbacks.

The existing Command/Event/UnreliableEvent trio, registry, exact schemas, Ready gate, wire budget, rate limiter and replay window are reused. Non-Class-A replay entries now also bind the private server ProfileSession object; replaced-session duplicate requests cannot return a cached success. Native Player removal still forgets bounded network records. No private session/consent/expiry outcome can be supplied by payload. Class A `Session.RequestResync {domain="party"}` and Ready handshake deliver recipient-only readback.

The full `Social.StateChanged` Party snapshot carries a monotonic recipient projection revision and `{allowInvites, party?, incoming, rejoin?}`. Party data contains GUID, membership revision, leader and up to four `{userId,present}` members. At most two pending incoming invites contain server identity, Party/revision, inviter, `Pending` status and immutable server-monotonic `expiresAt`; a returning reservation has Party/current revision/deadline. Expiry/decline/invalidated consent removes the item in a newer full snapshot. View revisions remain coherent when the deadline has not changed, and stale snapshots cannot restore departed membership. Server/client validate the same exact projection and reliable wire budget; store copies cannot mutate its source.

The native diagnostic panel is collapsed initially, survives avatar reset and offers only these bounded actions. Incoming data never selects input focus or opens a modal. Numeric target input is an ID intent, with no Party names/chat/user-authored public text. Native UI suffices; no new visual asset/material pipeline is needed. Final social UI belongs to PQL-3/PQL-8. Event/co-op/trade/commerce fields, reward multipliers and future cosmetic/status authority are absent.
